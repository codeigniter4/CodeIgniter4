Breaking Changes

File Cache deleteMatching() No Longer Matches Subdirectories

For security reasons, FileHandler::deleteMatching() now matches the pattern against the names of files in the cache directory only. See the Security advisory GHSA-9hf2-g3w9-pfmp for more information.

Previously, the pattern was appended to the cache path and passed to glob(), so a pattern containing a directory separator, such as dir/key_*, also deleted matching files in a subdirectory of the cache directory. Such a pattern now never matches anything and the method returns 0.

Most applications are not affected. The File handler stores every cache item directly in the cache directory, and the default Config\Cache::$reservedCharacters forbid / and \ in cache keys, so cache items could not be stored in subdirectories. If your application places its own files in subdirectories of the cache directory and removed them with deleteMatching(), delete them directly instead, for example with the delete_files() helper function.

Model Field Protection for replace()

For security reasons, Model::replace() now applies field protection:

  • With protection enabled, fields outside $allowedFields are discarded except for a supplied primary key. Define a non-empty list of fields callers may assign.

  • Non-empty input reduced by filtering to no data or only its primary key now raises a DataException. Review calls to ensure they supply allowed data.

  • For trusted operations requiring other columns, explicitly disable protection with protect(false) and restore it with protect(true) afterward.

See replace() for details and replacement-specific precautions.

Named Binds Are No Longer Replaced Inside Quoted Values

For security reasons, named bind placeholders (:name:) are now replaced only where the SQL parser would see them as part of the query. A placeholder that appears inside a quoted string ('...', "...", $$...$$ on PostgreSQL, q'[...]' on Oracle), inside a quoted identifier (backticks, "...", and [...] on SQL Server and SQLite), or inside a SQL comment (--, /* */, and # on MySQL) is now left untouched. This makes named binds behave the same way as question mark binds, which have always ignored markers inside quoted strings. See the Security advisory GHSA-25rf-99hr-7pmr for more information.

Previously, such placeholders were replaced as well, so a value that was already escaped and rendered into the query (for example a subquery, a custom where() string built with $db->escape(), or the WHERE binds of deleteBatch()) could be mixed with the value of another bind.

This change only concerns queries that place a placeholder inside a quoted string, a quoted identifier, or a comment. With the default escaping, such a placeholder never produced the intended SQL, because the quotes of the escaped value ended up inside the literal or identifier (for example LIKE '%:name:%' compiled to LIKE '%'Rick'%'). In practice, the only working queries that change their behavior are those that disable escaping for a bind, either with the third parameter of $db->query() or by passing a RawSql value, and rely on the placeholder being replaced inside a quoted string, a quoted identifier, or a comment: the placeholder is now left in the query literally. For example, the following used to search for %Rick% and now searches for the literal string %:name:%:

$db->query("SELECT * FROM users WHERE name LIKE '%:name:%'", ['name' => ['Rick', false]], false);

Move the quotes into the bound value instead, so that the value is escaped as a whole:

$db->query('SELECT * FROM users WHERE name LIKE :name:', ['name' => '%Rick%']);

Behavior Changes

Filename Sanitization

sanitize_filename() and Security::sanitizeFilename() now remove all backslashes. Single backslashes between ordinary characters were already removed in previous versions, so paths such as folder\file.txt produce the same result. Ordinary filenames and relative paths with forward slashes are also unchanged. Results can differ for repeated backslashes, literal \0 sequences, and inputs where removing backslashes exposes sequences stripped by the sanitizer.

Use forward slashes (/) for relative paths passed with $relativePath = true, including on Windows. If your application stores or compares sanitized filenames created from these inputs, check for changed results and possible filename collisions.
